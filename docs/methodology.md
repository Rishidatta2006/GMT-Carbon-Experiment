# Experimental Methodology & Scientific Framework

**Project:** Python Application Carbon Footprint Analyzer Using Green Metrics Tool (GMT)  
**Standard:** Green Software Foundation Software Carbon Intensity (GSF SCI) & ISO/IEC 21031  
**Measurement Boundary:** Operational Software Carbon Emissions (Scope 2 & Host Energy)

---

## 1. Experimental Overview & Scientific Principles

Software does not directly consume electricity; it commands physical hardware (CPUs, DRAM, network interfaces, power supplies) to execute instructions. This execution induces electrical current through semiconductor gates, generating heat and dissipating energy.

The primary objective of this experiment is to isolate, measure, and analyze the energy consumption and carbon emissions generated by two contrasting computational workloads running on identical Python runtimes within containerized execution boundaries:

1. **LOW Workload:** Minimal CPU activity executing a controlled periodic duty cycle (10ms compute / 90ms sleep, ~5–15% CPU load).
2. **HIGH Workload:** Continuous CPU-intensive cryptographic SHA-256 hash chaining (100% single-core saturation).

---

## 2. Controlled Variables & Scientific Isolation

To ensure repeatability, reproducibility, and scientific validity, all independent variables except workload intensity are strictly controlled:

| Variable | Control Mechanism | Justification |
|---|---|---|
| **Execution Duration** | Fixed at 30.0 seconds ($\pm 0.05$ s via monotonic high-resolution timer) | Eliminates duration as a confounding factor; enables direct power (W) and energy (J) normalization. |
| **Runtime Environment** | Official Python 3.12 (`python:3.12-slim` base image) | Eliminates bytecode compiler variations and runtime optimizations across versions. |
| **Container Sandbox** | Identical OCI container configuration & non-root user (`gmtuser`) | Ensures uniform OS filesystem layers, kernel isolation, and namespace boundaries. |
| **Hardware Measurement Node** | Dedicated GMT measurement cluster node (bare-metal Intel/AMD CPU) | Eliminates hypervisor noise, vCPU oversubscription, and virtualization artifacts. |
| **Measurement Stabilization** | 5.0-second baseline stabilization sleep prior to execution | Allows CPU package frequency, dynamic voltage, and RAPL energy registers to settle to idle baseline. |
| **Workload Determinism** | Fixed cryptographic seeds and constant batch iterations | Guarantees identical execution logic across independent experiment runs. |

## 3. Physical Energy Measurement Architecture

Energy measurement at the software layer is performed using hardware registers and kernel resource accounting coordinated by the **Green Metrics Tool (GMT) ScenarioRunner**:

```
+-------------------------------------------------------------------+
|                   Green Metrics Tool (GMT)                        |
|   +-----------------------------------------------------------+   |
|   |         ScenarioRunner Lifecycle (BOOT -> RUNTIME)        |   |
|   +-----------------------------------------------------------+   |
|         |                                           |             |
|         v                                           v             |
|   [Linux cgroups v2]                         [Hardware RAPL]      |
|   - CPU cycles & instructions                - CPU Package (PKG)  |
|   - Memory RSS & page faults                 - Core Domain (PP0)  |
|   - I/O & Network throughput                 - DRAM Controller    |
+---------|-------------------------------------------|-------------+
          |                                           |
          +-------------------+   +-------------------+
                              |   |
                              v   v
            +---------------------------------------+
            |  Target OCI Container (Python 3.12)  |
            |  - LOW Workload: Duty Cycle (~10%)    |
            |  - HIGH Workload: SHA-256 (100%)      |
            +---------------------------------------+
```

### 3.1. Intel / AMD Running Average Power Limit (RAPL)
RAPL provides micro-architectural hardware counters that report accumulated energy consumption with millisecond granularity across specific power domains:
* **Package (`PKG`):** Encompasses entire CPU die including all execution cores, L3 caches, memory controllers, and uncore logic.
* **Power Plane 0 (`PP0`):** Isolated energy consumption of CPU compute cores.
* **DRAM:** Energy consumed by dynamic random-access memory modules controlled by the integrated memory controller.

Energy in Joules ($J$) is sampled at high frequency:
$$E = \int_{t_{\text{start}}}^{t_{\text{end}}} P(t) \, dt$$
where $1 \text{ Watt-hour (Wh)} = 3600 \text{ Joules}$.

### 3.2. Linux Control Groups (cgroups v2)
To attribute system-wide energy accurately to the target application, GMT leverages Linux `cgroups v2` to monitor:
* `cpu.stat`: Total CPU execution time in user mode and system mode.
* `memory.current` / `memory.peak`: Precise physical memory occupancy (RSS).

## 4. Software Carbon Intensity (GSF SCI) Calculation

Carbon emissions ($\text{CO}_2\text{e}$) are derived from energy measurements using the **Green Software Foundation (GSF) Software Carbon Intensity (SCI)** standard:

$$\text{SCI} = \frac{(E \times I) + M}{R}$$

Where:
* **$E$ (Operational Energy):** Total energy consumed during workload execution (measured in kilowatt-hours, $\text{kWh}$).
* **$I$ (Grid Carbon Intensity):** Regional carbon intensity of the electricity grid powering the hardware node ($\text{g CO}_2\text{e} / \text{kWh}$).
* **$M$ (Embodied Carbon):** Carbon emissions incurred from hardware manufacturing, transport, and recycling amortized over device lifespan.
* **$R$ (Functional Unit):** The unit of work (e.g., per 30-second execution run).

For operational comparisons in this project, operational emissions are computed as:
$$\text{Operational Emissions } (\text{g CO}_2\text{e}) = \left(\frac{E_{\text{Joules}}}{3{,}600{,}000}\right) \times I$$

### Crucial Distinction: Energy vs Carbon
* **Energy Consumption ($J$ or $\text{Wh}$)** is an intrinsic physical property of hardware execution dictated by code efficiency, algorithmic complexity, and hardware architecture.
* **Carbon Emissions ($\text{g CO}_2\text{e}$)** is an extrinsic environmental consequence dependent on the regional and temporal generation mix of the electric grid.
* Two identical software runs consuming identical energy will produce drastically different carbon emissions if executed on a coal-heavy grid ($800 \text{ g/kWh}$) versus a hydro/nuclear grid ($20 \text{ g/kWh}$).

## 5. Non-Linearity: Why CPU Usage $\neq$ Carbon Emissions

A frequent fallacy in sustainable computing is assuming that $10\%$ CPU utilization implies $10\%$ of peak energy consumption. This ignores fundamental electrical principles:

$$P_{\text{total}} = P_{\text{static}} + P_{\text{dynamic}}$$

1. **Static Power Dissipation ($P_{\text{static}}$):**
   Sub-threshold transistor leakage current, voltage regulators, fans, motherboard chipsets, and RAM refresh cycles persist continuously whenever the machine is powered on, even at zero software load.
2. **Dynamic Power Dissipation ($P_{\text{dynamic}}$):**
   $$P_{\text{dynamic}} = \alpha \cdot C \cdot V^2 \cdot f$$
   where $\alpha$ is activity factor, $C$ is capacitance, $V$ is supply voltage, and $f$ is operating frequency.
3. **Dynamic Voltage and Frequency Scaling (DVFS):**
   Under the HIGH workload, the CPU governor raises frequency $f$ and voltage $V$. Because dynamic power scales with the *square* of the voltage ($V^2$), power consumption increases non-linearly.
4. **Energy Proportionality Gap:**
   Servers are rarely energy-proportional. An idle server often consumes $30\text{--}50\%$ of its peak power. Therefore, running software at low load still incurs a substantial baseline energy cost.

## 6. Measurement Uncertainty & Validity Threats

When conducting reproducible software benchmarks, several potential sources of noise must be managed:

1. **Host Daemon Noise:** Background OS tasks (cron, systemd, networking) can skew CPU metrics. Mitigated by dedicated bare-metal nodes and pre-run baseline stabilization.
2. **Thermal Throttling:** Prolonged high CPU loads elevate die temperature, triggering frequency down-throttling. Mitigated by keeping benchmark duration at 30 seconds with cooldown pauses.
3. **Container Boundary Overhead:** Docker virtualization overhead is negligible ($<1\%$) for compute-bound tasks, but I/O and process creation can introduce jitter.
4. **RAPL Overflow:** Energy counter registers have fixed bit widths and roll over periodically. GMT's background daemon samples frequently enough to handle roll-over arithmetic cleanly.
